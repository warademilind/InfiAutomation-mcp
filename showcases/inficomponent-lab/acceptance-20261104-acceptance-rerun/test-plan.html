Execution sequence and isolation

  1. Call MCP doctor, launch owned packaged Electron and inspect session_info, ui_windows, ui_menus and all 21 page snapshots.
  2. Import and read the complete requirements, save requirement-linked plan, generate schemaVersion 2 suite with healing off.
  3. Run LAB01–LAB16 sequentially. Assert positive, negative, boundary, state-change and persistence outcomes.
  4. Run supplementary controls and persistence across owned launches. Run reset only after persistent-state cases finish.
  5. Launch a separate profile without --test-mode and verify disabled UI reset plus HTTP 403.
  6. Run optional CDP and explicit Windows UIA checks in a separate newly created profile; record connection capability boundaries.
  7. Poll test_status to completion, retrieve report_get and traceability_get, retain first-run failures and fresh rerun evidence.

Cases begin with a ready Workspace assertion before native IPC navigation. Navigation waits for the destination page. The suite never edits the application or enables healing, and no visual baselines are generated or approved.

Coverage and acceptance gates

The core gate requires all 16 LAB cases passing explicit assertions with zero healed outcomes. Native export additionally requires an existing parseable JSON file with 18 seeded customers. The connection gate requires runtime/menu evidence, a native API capability rejection over CDP, preserved state after detach, and observed UIA OS dialog controls.

Safety gates: only fresh synthetic profiles; owned backend/CDP configuration at loopback; enabled context isolation, renderer sandbox and web security; test-mode reset confirmation; reset denial outside test mode; no automatic baseline approval. Runtime listener socket inspection and exploit testing are outside the recorded configuration audit.

Interactive follow-ups must be completed before claiming exhaustive supplementary coverage. The report can show core acceptance passed while these remain not run.
